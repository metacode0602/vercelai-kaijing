# GPURun Sandbox Overview

<Callout type="info">
  GPURun Sandbox offers isolated, stateful execution environments designed for AI agents. It enables running code, installing dependencies, accessing files, using browsers, and preserving state across sessions without infrastructure management.
</Callout>

GPURun Sandbox is a managed execution environment for AI agents that need to run code, use browsers, work with files, and preserve state across sessions. It gives each agent an isolated runtime without requiring you to manage infrastructure.

***

The platform is built on the following core concepts:

## Core Concepts

### Sandbox

An isolated execution environment where agents perform tasks. Each has its own filesystem and runtime, allowing agents to run commands, manage files, install dependencies, and handle browser-based workflows.

</div>

A sandbox moves through three states: Running, Paused, and Killed.

* **Running** — the sandbox is active and can execute commands and serve connections.
* **Paused** — the sandbox is suspended; its filesystem and memory state are preserved and billing for compute stops. It can be resumed back to Running (typically in about a second).
* **Killed** — the sandbox is terminated and its resources are released. A killed sandbox cannot be resumed.

Two settings drive the transitions out of Running:

* **Timeout** — the maximum lifetime of the sandbox. It counts down from creation regardless of activity; when it expires the sandbox is stopped by default, or paused if you configure the lifecycle accordingly. See [Timeout Handle](/guides/sandbox-timeout-handle).
* **Idle timeout** — fires only when no client has been connected for the configured duration, automatically killing or pausing the sandbox. See [Idle Timeout Handle](/guides/sandbox-idle-timeout).

On timeout or idle timeout you can choose **pause** (so the sandbox can be resumed later, optionally with auto-resume) instead of **kill**. When paused, resuming restores the sandbox to Running with its state intact; when killed, the sandbox and its data are gone.

### Template

Defines the starting environment for a Sandbox. Templates ensure consistency across multiple Sandboxes with predefined dependencies, configuration, and setup steps.

### Snapshot

A Snapshot saves the current state of a Sandbox as a reusable environment. Snapshots are useful after you have configured a Sandbox, installed dependencies, or generated files that you want to reuse. New Sandboxes can be created from a Snapshot without repeating the same setup steps.

### Secret

Secrets are a secure way to store and use sensitive values — such as API keys, tokens, and passwords — inside a GPURun Sandbox. They are encrypted and managed within the scope of the current team, letting code running in a sandbox authenticate to external services without hardcoding credentials in source code, snapshots, templates, or sandbox environment variables.

### Regions

GPURun Sandbox currently provides access through the following regions:

| Name          | Version | Domain                       | Description                                    |
| ------------- | ------- | ---------------------------- | ---------------------------------------------- |
| us-phx-1      | v2      | `us-phx-1.sandbox.gpurun.ai` | Default region (used by the current SDK / CLI) |
| us-virginia-1 | v1      | `sandbox.gpurun.ai`          | Specified via environment variable             |

The **v2** region (us-phx-1) is the **default** used by the current SDK and CLI. It adds capabilities such as **Secrets** and **Snapshots** on top of v1 and provides a more complete feature set, so it is recommended to use v2 first.

The SDK and CLI documented here are compatible with both v1 and v2 regions. To use the **v1** legacy region instead, configure the environment variable `GPURUN_DOMAIN`:

```bash theme={"system"}
export GPURUN_DOMAIN=sandbox.gpurun.ai
```

## When to use GPURun Sandbox

Intended for workloads requiring isolated environments to execute tasks, maintain state, or reuse prepared setups. Common use cases include:

* Coding agents that run code, install packages, and execute tests
* Browser agents that automate web workflows
* Data analysis agents that process files and generate reports
* Research or RL workloads that need many isolated environments

***

## Pricing

Billing is per-second for CPU and RAM. Storage—covering templates, paused sandboxes, and snapshots—incurs daily charges. Additional details are available on the [pricing page](/guides/sandbox-pricing).
