## 1. 结论摘要

1. 原型中的下拉框分三类：
   - **已有维护页**：平台基础资料、基础数据字典、供应商管理、店铺连接、仓库与库位、商品 SPU/SKU、组织成员/角色权限。原型多数仍直接写死示例值，需要后续改为读取维护数据。

### 3.1 包装规格与箱规：为什么不建议直接合并

先用一句话区分：

- **包装规格**回答“这件商品怎么卖”：单件、两件装、礼盒装。
- **箱规（packaging_specs）**回答“这批货怎么发”：一箱装几件、箱子多大、多重、箱规编码是什么。

不建议直接合并的原因：

1. **层级不同**：包装规格是商品/SKU 的属性；箱规是采购、入库、运费测算使用的物流属性。一个 SKU 可以按单件卖，但按 20 件一箱发。
2. **字段不同**：箱规需要长宽高、毛重、净重、箱数；包装规格通常只需要一个名称。合并后商品表单会多出一堆物流字段，运营填起来更累。
3. **维护人不同**：包装规格由商品运营维护；箱规由采购/仓管维护。合并成一张表会让两个角色互相等对方。
4. **不合并也不会重复**：可以保留两张表，但建立关联——箱规可选“适用包装规格”，商品 SKU 只选包装规格。名称只在属性字典维护一次，箱规引用它，而不是复制它。

**结论：不合并主数据，只建立关联。** 商品 SKU 只选包装规格，箱规引用包装规格；箱规在独立「箱规管理」页维护。

### 3.2 结算单状态：为什么建议受控而不是自由切换

结算单状态不是普通下拉值，而是财务对账状态机：

- `待匹配`：平台账单还没和订单/SKU 对上。
- `差异待处理`：金额、佣金、运费或退款有差异，需要人处理。
- `已确认`：对账完成，进入利润和结算报表。

如果允许有权限的人自由切换，会有三个风险：

1. 绕过差异校验，把“差异待处理”直接改成“已确认”，利润被高估或低估。
2. 没有原因和审计记录，月底对不上账时无法追溯是谁改的。
3. 状态和实际单据脱节，后续退款、补扣无法自动回写。

**结论：不允许自由切换，只提供受控动作**——“提交差异复核”和“确认对账”；差异未归零不能确认，确认后锁定期间，操作原因写入审计记录。

## 4. 建议的菜单落位

```text
商品中心
  · 商品库SPU
  · 品类树            ← 多级品类独立主数据
  · 内部SKU
  · 供应商货号        ← 供应商读取「采购中心 · 供应商管理」
  · 属性字典          ← 品牌/颜色/尺码/履约模式/仓库类型；品类树单独维护
  · 商品评论

采购中心
  · 采购申请
  · 采购审核
  · 采购单
  · 到货质检入库
  · 供应商管理        ← 商户供应商主档（已实现）

仓库中心
  · 库存汇总
  · 仓库与库位        ← 仓库/库位
  · 库区管理          ← 仓库下的独立库区主数据
  · 入库单
  · 出库单
  · 库存流水
  · 盘点与调整
  · 库存预警

售后中心
  · 取消与退款
  · 退货质检与回库

成本财务
  · SKU成本
  · 平台结算对账
  · 订单与SKU利润
  · 承运商管理        ← 租户自维护承运商主档
  · 箱规管理          ← 运输包装独立主数据，引用包装规格
  · 运费测算          ← 承运商/线路/HS/箱规参考数据

设置
  · 店铺连接
  · 平台应用配置
  · 平台基础资料      ← 平台/国家站点/仓库/币种
  · 基础数据字典      ← 统一字典入口（与商品中心属性字典同页）
  · 数据导入          ← 导入批次与错误行
  · 导入模板          ← 模板版本/字段/重复与回滚策略
  · 接口日志
  · 角色权限
  · 组织成员          ← 人员下拉来源
```

**建议原则：**

- 能复用「基础数据字典」的枚举，优先在字典中新增分类，不新增菜单；只有需要独立主档（供应商、承运商、导入模板）时才建独立页面。
- 系统状态枚举默认只读；物流/包裹/拣货允许人工补录事件并标记来源（已确认），平台接入状态由平台运营维护（已确认），结算状态流转待确认。
- 主档数据（供应商、SKU、店铺、仓库、库位、成员）必须由现有维护页提供，原型下拉框统一读取，不再写死示例值。
- 所有下拉项只显示启用值；停用值保留历史记录但不出现在新建表单中。
